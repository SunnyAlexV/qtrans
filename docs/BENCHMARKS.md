# Benchmarks

Generated by `tools/benchmark.py`: run it to reproduce every number here. **All benchmarks measure already-built code; every function is verified before timing, and the reported verification counts are shown beside its result.** A speed-up is never quoted for a translation that differs from Python.

**Across the 87 verified example functions, on the machine below, standalone generated C++ had a median speed-up of 18× over the Python; results ranged from 0.9× to 3,231×, depending on the workload and the baseline.** Quote it that way: qtrans is not "18× faster" in itself. The speed-up depends on the function, the input size, the libraries it calls, the hardware, and whether the Python baseline is a plain loop or vectorised NumPy (see *Workloads*).

## What is timed

- **Per-call time of already-built code only.** Translating, compiling, building the bindings and importing them are not in any timing; they are paid once and are listed under *One-off costs*.
- **Inputs built beforehand.** The arguments are made once before timing (NumPy arrays for Python, C++ values for C++); the timed calls run on them.
- **Warm-up.** One untimed call, then runs of 1, 4, 16, ... calls until one lasts at least 0.1 s; only that run is timed, and divided by its number of calls. The shorter runs before it warm up too. Calls timed per round, over every function here: 16 to 268,435,456.
- **No call can be optimised away.** The C++ call is in the same translation unit, so the compiler may inline it, as in any C++ program that includes the header. The arguments are hidden from the optimiser on every call (volatile scalars, an empty asm barrier on arrays and objects) and every part of the result goes into a checksum that is printed. A C++ time of a few nanoseconds is real: what is left once Python's call is gone is a handful of instructions.
- **Rounds.** 7 rounds per function, Python and C++ taking turns; the **median** is reported. *Spread* is the interquartile range over the median, of the noisier side: robust to one slow round. This runs on a shared virtual machine, and a spread of tens of percent is the machine, not the code; it is why medians of several rounds are reported.

**Verified (m/i/k/x)** = matches / ill-conditioned (Python's own answer moves by as much under a 4-ULP nudge of the inputs, so the case can't tell) / known differences (documented in the README, each where it can apply) / mismatches, over the function's hand-picked and random cases. Rows marked **†** have known differences, rows marked **‡** ill-conditioned cases: their timings stand, but not every case of theirs is a plain match.

## Workloads

The same book priced three ways answers whether the Python baseline already uses NumPy. "Compiled, from Python" is the `qtrans bind` module called from Python on the same arguments: NumPy arrays converted in, the result converted back.

What this shows:

- Against a plain Python loop the C++ is 19× faster (`book_loop`) and 6× (`ytm_book`). Against NumPy-vectorised Python the gain is 2.2× (`book_numpy`): NumPy already runs its loops in C. Replacing a Python loop with compiled code is not the same as beating well-vectorised NumPy by that much; the compiled loop is 1.6× faster than the vectorised Python.
- `mc_call` is slower in C++ (2.31 ms against 1.82 ms). Taken apart, the draws are on a par (1.03 ms against 1.38 ms), and `np.exp` is not (454.1 µs against 126.4 µs): NumPy has its own SIMD exp (AVX-512 on this CPU), and the C++ calls the C library's exp per element, so it agrees with Python's math.exp and only to rounding with NumPy's. Porting NumPy's exp would make it both faster and bit-identical on such CPUs; it is on the roadmap.
- Called from Python through `qtrans bind`, one scalar `bs_call` takes 138 ns against 34 ns in C++: the difference is Python's call and the conversions, and it is still 4× faster than the Python function. On the books of options and bonds the bound module is within 18% of the C++ alone: converting 10,000-element arrays is small next to the work. The bindings cost most, in proportion, on the shortest calls.
